# 消费品竞品监控实践：从企业需求到可核验的竞品报价体系

以跨境配镜行业为例。本项目来自 FDE 企业真实需求实践，由企业导师、项目主理人与项目成员共同完成。本文讲述需求如何变化，以及为什么最终交付聚焦报价；实现细节见[系统架构](architecture.md)。

## 从一个看似简单的价格问题开始

消费品企业做竞品监控，需要知道竞品现在卖多少钱、不同配置怎样改变报价、过去是否调整过价格，以及这些结论能否再次核验。企业最初还希望观察商品趋势和商品可能获得关注的渠道，以辅助选品、产品策略和营销决策。

进入企业场景后，我们发现网站表层显示的价格，与可用于业务判断的竞品数据不是一回事。商品页可能只展示镜框价格；购买流程中的镜片类型、材料、折射率等选择会改变报价。同样，搜索热度、社媒内容或站点访问估算，也无法直接给出某一款商品的销量、渠道流量和转化来源。

因此，项目没有先把原始需求逐条变成采集任务，而是先问：**企业需要作出什么判断，公开数据能支撑到哪一步？** 可以从公开页面核验的商品身份、镜片配置及购买流程报价成为当前重点。单品渠道归因缺少相应粒度的可靠数据，暂不输出结论。

## 需求收敛的过程

| 企业希望回答的问题 | 当前可获得的材料 | 项目中的处理 |
| --- | --- | --- |
| 竞品某款眼镜卖多少钱 | 官网商品页、实际配置流程、购物车商品行 | 核对商品身份后，按支持配置走到购物车核价 |
| 配置怎样影响报价 | 页面可见的镜片类型及后续选项 | 保存实际选择路径，分别记录已核价和未完成配置 |
| 价格是否发生变化 | 按日保存的同口径报价 | 仅比较可比历史；缺少基期时不输出涨跌百分比 |
| 哪些渠道带来商品关注 | 搜索、社媒与站点级公开线索 | 线索可以提示后续调查，不推断单品流量或转化 |

最终问题被收敛为：**如何将公开、异构且不断变化的竞品商品信息，整理成口径一致、可比较、可追溯来源的报价数据？** 跨境配镜是这套问题的验证场景；其配置多、市场不同，能直接暴露“价格只是一个数字”这种理解的不足。

## 为什么核对商品，也核对报价口径

用户以品牌和商品名发起任务。已收录商品使用已确认的官方链接；新商品先获得候选页面，再核对官网名称、型号、配色和购买方式。搜索结果的排序不能代替商品确认。目标商品不明确时，流程应停在澄清阶段。

确认商品后，系统按当前支持的镜片路径模拟购买，在购物车读取商品行的镜框与镜片优惠前单件小计，并保存配置、市场、币种、采集时间和证据。这一口径比商品页裸价更接近指定配置的实际报价，但仍不是结账后的最终支付价：税费、运费和优惠资格没有由当前核价流程验证。

价格变化同样需要边界。两个数字即使相等或都以美元显示，也可能属于不同配色、镜片技术、市场或报价条件。项目仅在商品、SKU／配色、处方、配置、市场、币种和报价口径相同的情况下讨论历史变化；没有可比较记录时显示缺口，而不是生成一个看似完整的涨跌数字。

## 形成的交付链路

```text
商品确认 → 配置规划 → 站点执行 → 购物车核价
         → 证据留存 → 结构化记录 → 历史比较 → HTML 看板
```

用户输入品牌与商品后，Skill 负责整理任务、确认市场和采集范围、调用采集能力、检查结果。浏览器自动化负责页面交互与购物车核价；数据处理和看板负责把商品、配置、时间、来源及失败状态组织在一起。Skill 的作用是把原本分散的一次性步骤变成可重复调用的工作流，而不是替代实际执行代码。

一条对外展示的报价可以回到商品页面、选择路径、采集时间、购物车页面及截图。证据既服务使用者复核，也帮助成员在弹窗、页面状态变化、配置不可达或长时间运行失败后定位问题。同日监测报价在满足条件时可以复用，但必须保留原观测时间和复用标记。看板生成成功也不意味着所有配置都已采齐；失败与未覆盖路径需要明确呈现。

## 这次实践留下的判断方法

项目让成员练习的并不只是网页自动化。首先要把“我要渠道流量”之类的模糊诉求追问到具体业务判断，再检查数据来源与粒度。拿不到的数据应明确说清，不能为了让看板完整而制造数字。每个价格要说明对象、配置、市场、时间、计算口径和来源；每个结论要能回到原始证据。

当前交付包括已支持场景的自动报价采集、证据、结构化数据、历史观测和可筛选 HTML 看板。单品销量与渠道归因、更多站点及更长的完整历史仍需新的数据来源或持续采集。产品边界见[当前限制](limitations.md)，已有本地运行规模与正式评测的区别见[评测说明](evals/benchmark.md)。
