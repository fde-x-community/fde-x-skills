# fde-x-skills 一期改造清单

> 状态：实施中。本文依据仓库现状、`github需求.png` 与 `聊天文档.txt` 整理；勾选项表示已在当前分支实现，未勾选项仍待实施或决策。

## 1. 改造目标

让第一次进入仓库的人在一分钟内明白：这里收集的不是通用提示词，而是**从真实企业需求中提炼、经脱敏并可验证的 Agent Skill**。让贡献者能先提交业务问题，再与维护者判断是否值得做成 Skill；让评审者能同时检查业务价值、可复用边界和包质量。

一期完成后应形成一条清晰路径：

`企业需求 → 脱敏的问题 Issue → 范围与成功标准 → Skill PR → 验证证据 → 收录与持续维护`

仓库仍以兼容 [Agent Skills 规范](https://agentskills.io/specification)的 `SKILL.md` 作为可安装单元。企业场景、验证记录和成熟度是本仓库额外的治理信息，不应被误写成开放标准的必需字段。

## 2. 现状与改造原则

| 现状 | 影响 | 处理原则 |
| --- | --- | --- |
| README 先呈现空的 Skill 索引，项目价值和任务链在后面 | 新访客难以迅速理解为何这是企业需求仓库 | 先展示定位、适用人群和一条明确标注为示意的需求转化案例，再展示目录 |
| 新 Skill Issue 先问名称、触发语和包结构 | 尚未澄清业务问题就提前锁定实现方式 | 将“提交企业需求”和“提出 Skill 方案”分成两种入口 |
| PR 模板以结构勾选项为主 | 评审者看不到需求来源、效果与泛化边界 | 以“问题—方案—证据—边界”为主线，机器能检查的事项交给 CI |
| 每个新 Skill 必须满足完整十二层结构 | 有利于成品质量，但会抬高需求提出阶段的门槛 | 保留 Skill 收录门槛，降低需求 Issue 门槛；暂不整体推翻现有结构 |
| 文档称额外 frontmatter 字段会被标准解析器拒绝 | 与开放规范不符 | 明确这是本仓库当前收录策略，并审视是否需要允许标准字段 |
| Windows 下 `validate.mjs` 与 `build-index.mjs` 入口未运行 | 本地校验可能假通过 | 修复入口判断并加跨平台验证 |

一期不追求 Skill 数量，也不把企业原始材料公开作为收录条件。没有可公开的真实案例时，用明确标注的**示意案例**说明方法，不冒充已验证成果。

## 3. 任务清单

### P0：修正校验可靠性与事实表述

- [x] **P0-1 修复脚本在 Windows 下静默退出。** 修改 `scripts/validate.mjs`、`scripts/build-index.mjs` 的直接运行入口判断，使用规范化文件路径或 `pathToFileURL`，避免比较 `import.meta.url` 与手工拼接的 `file://` 字符串。分别验证成功、故意制造失败、`--check` 检出索引漂移三种情况；CI 与本地均应返回正确退出码。不要把“没有 Skill”误判成校验失败，但要明确提示“当前只完成工具链自检，尚未验证任何 Skill”。
- [x] **P0-2 更正 frontmatter 说明。** 修改 `README.md`、`CONTRIBUTING.md`、`templates/skill/SKILL.md`、`.github/PULL_REQUEST_TEMPLATE.md` 和校验器报错。官方规范要求 `name`、`description`，也允许 `license`、`compatibility`、`metadata` 等可选字段。当前决定严格只收 `name` 和 `description`；准确表述为“仓库收录规则”，并在兼容性调研中列明与开放规范及平台可选字段的冲突。
- [x] **P0-3 核对 README 可验证声明。** 对“39+ 个 harness 直接读取”等数字或兼容性措辞提供可维护的来源；若无法核实，改为不依赖数量的准确描述。区分“格式兼容”和“在具体客户端完成验证”。

**验收：** Windows 和 GitHub Actions 对相同输入给出一致的通过或失败结果；README 与贡献文档不再把仓库政策说成标准要求。

### P1：把企业需求放到仓库入口

- [x] **P1-1 重排 README 首屏。** 第一屏依次回答：仓库解决什么问题、适合谁、一个需求如何变成 Skill、当前有哪些可用 Skill。空仓状态明确写“尚无已收录 Skill”，并提供“提交需求”“参与共建”的链接。保留生成索引标记，避免与 `build-index.mjs` 冲突。
- [x] **P1-2 增加一条明确标为虚构的示意案例。** 用短案例展示：角色与场景、原有流程痛点、Skill 接收的输入与交付的输出、人工介入点、验证方式、不可覆盖的边界。若没有已授权的真实公开案例，标题标为“示意流程”，不写企业名称或未经证实的效果数字。
- [x] **P1-3 给出清晰的参与路径。** 分别引导企业需求方、业务专家、Skill 作者和审查者。每条路径只给下一步动作，详情放到 `CONTRIBUTING.md`。

**验收：** 未接触过项目的读者无需先理解“十二层结构”，就能复述仓库价值和提交入口；README 的索引仍可由脚本生成。

### P1：重做 Issue 入口与需求分流

- [x] **P1-4 新增“企业需求”Issue 表单。** 只把业务问题描述设为必填；指标与口径、计算和边界规则、成果必须包含的内容均作为可逐步补充的字段。允许写“待澄清”，避免逼迫需求方一次填完或伪造确定性。
- [x] **P1-5 调整现有 `new-skill.yml`。** 将它定位为“已有需求后的 Skill 方案”，要求关联需求 Issue，说明为何现有 Skill 不够用、触发与非触发场景、可复用部分与项目专属部分。新 Skill 名称可以建议，但不作为提出企业问题的前置条件。
- [x] **P1-6 写出分流规则。** 需求不清先澄清；重复需求优先扩展已有 Skill；仅一次性的客户定制任务可以记录经验，但暂不承诺收录为通用 Skill；涉及客户机密的资料只提交脱敏摘要或合成样例。

**验收：** 一个不会写 `SKILL.md` 的业务参与者也能提交合格需求；维护者能据 Issue 判断是否进入 Skill 开发。

### P1：把 PR 变成可评审的交付说明

- [x] **P1-7 重写 PR 模板。** 通用部分包括关联 Issue、变更摘要、验证命令与结果、风险、AI 辅助披露、脱敏确认。Skill PR 额外回答：原始需求是什么、哪些判断被提炼为可复用方法、相对既有做法的改进证据、测试覆盖、适用与不适用场景、人工接管点。仓库工具链和纯文档 PR 可填“不适用”，不强迫编造业务证据。
- [x] **P1-8 把结构检查清单压缩为少量确认项。** `name`、目录、占位符、索引漂移等由 CI 自动判定；PR 保留 CI 无法判定的内容，例如样例是否真实反映问题、是否泄露客户信息、脚本副作用是否被逐行审查。
- [ ] **P1-9 明确审查角色。** 业务或领域审查者确认问题定义与输出可用性；技术审查者确认兼容性、脚本安全和回归测试。现有“两位维护者批准”规则需要和 GitHub 实际可配置的分支保护或 CODEOWNERS 对齐，不能只写在文档里却无法执行。

**验收：** Reviewer 不打开全部文件也能先理解“为什么做、证据是什么、边界在哪”；PR 模板不与 CI 大量重复。

### P1：梳理 Skill 组织与成熟度

- [x] **P1-10 明确包内必需内容与仓库治理内容。** `SKILL.md` 是开放标准入口；`VERSION.json`、六类评估、日志契约等属于本仓库质量体系。贡献指南需解释每层解决的实际问题，以及何时豁免，避免读者把仓库私有规则当作跨平台要求。
- [ ] **P1-11 用一份完整样例验证脚手架。** 从一个可公开的脱敏需求出发，走完 Issue、`new-skill.mjs`、PR 模板、校验、索引生成。若无法取得真实案例，则先用合成样例验证工具链，明确其不代表业务有效性。
- [x] **P1-12 保留 `draft` 的诚实标注。** README 的索引应让读者一眼看懂 `draft`、`package_validated`、`operationally_validated`，且不要把结构检查通过等同于企业场景验证通过。

**验收：** 一名新贡献者按文档可走通完整流程；一名使用者能分辨“可安装”“结构通过”和“业务验证过”。

## 4. 实施顺序与交付批次

1. **批次 A：事实与工具修复。** 完成 P0-1 至 P0-3，先让本地和 CI 检查可信。交付脚本改动、必要测试和准确的规范说明。
2. **批次 B：需求入口。** 完成 P1-1 至 P1-6，交付 README、企业需求 Issue、调整后的 Skill 提案 Issue 与贡献指南。
3. **批次 C：贡献与评审。** 完成 P1-7 至 P1-12，交付 PR 模板、审查规则和一份流程样例。回头核对模板、脚本、README 是否说的是同一套规则。

当前工作先集中在 `feat/enterprise-skill-governance` 分支供整体评审，后续可按批次拆 PR。文档改动还需要业务参与者试填；若团队使用“ECQ”作为既有评审框架，应在确认其定义后再映射进 PR 模板，不自行假设含义。

## 5. 二期预留，不纳入本轮交付

- **Benchmark 接口：** 现有 `tests/scenario-matrix.json` 与成熟度字段可作为起点。二期再定义基线、指标、样本来源、复现实验环境和结果发布规则；一期不对外宣称性能提升。
- **Skill 市场分发：** 先维护标准 `SKILL.md` 与清晰许可，再研究各市场的收录规则、打包格式和审核流程。是否外发某个 Skill，取决于客户授权、脱敏程度和可复用价值，不能由 PR 合并自动触发。
- **影响力与贡献者展示：** 在有真实收录与可公开验证结果后，再设计案例页、贡献者署名和传播材料。

## 6. 参考依据

- [Agent Skills 开放规范](https://agentskills.io/specification)：包格式、必需与可选元数据。
- [Agent Skills 最佳实践](https://agentskills.io/skill-creation/best-practices)：让 `SKILL.md` 聚焦必要步骤，详细知识按需加载。
- [GitHub Awesome Copilot 贡献指南](https://github.com/github/awesome-copilot/blob/main/CONTRIBUTING.md)：收录边界、具体性、测试与贡献流程。
- [Agent Skills 项目贡献指南](https://github.com/agentskills/agentskills/blob/main/CONTRIBUTING.md)：区分讨论、Issue 和 PR，要求聚焦变更及可复核证据。
- [Microsoft PowerToys PR 模板](https://github.com/microsoft/PowerToys/blob/main/.github/pull_request_template.md)：关联问题、变更说明和验证步骤。

这些来源提供格式与治理方法；本仓库的企业需求证据链、脱敏要求和收录判断仍需按自身定位设计。
